## បញ្ជី Gate និងទម្រង់ប្រតិបត្តិការ

### ការទទួលយកបេក្ខភាព

លំហូរការងារ CI និង Quality Gates នីមួយៗបញ្ចេញលទ្ធផលវិនិច្ឆ័យដែលមានស្ថិរភាព៖ `Gate / CI` និង
`Gate / Quality`។ គោលការណ៍ទទួលយកដែលមានកំណែរបស់ពួកវារាយបញ្ជីរាល់ការងារ upstream
ថាជាការងារចាំបាច់ ឬជាការងារផ្ដល់យោបល់។ ការងារចាំបាច់ដែលអនុវត្តបាន ត្រូវតែជោគជ័យ៖ លទ្ធផលដែល
បាត់ អ被លុបចោល ត្រូវបានរំលង កំពុងរង់ចាំ និងមិនស្គាល់ មិនអាចកំណត់ PASS បានទេ។ ការចាត់ថ្នាក់
ដែលត្រឹមត្រូវថាសម្រាប់តែឯកសារ ឬសម្រាប់តែកាតាឡុក អាចធ្វើឱ្យ lane កូដមិនអាចអនុវត្តបាន;
PR ព្រាងមិនត្រូវបានទទួលយកជាបេក្ខភាពទេ។ ស្លាក `hotfix` មិនលើកលែងតម្រូវការភស្តុតាងឡើយ។

លំហូរការងារទាំងពីរគ្របដណ្ដប់លើ PR ទៅកាន់ branch main/release, ការ push ទៅ `main`, ការបញ្ជាដំណើរការដោយដៃ
និងព្រឹត្តិការណ៍ merge-group។ ការ push, ការបញ្ជាដំណើរការ និង merge-group ដំណើរការជម្រើសពេញលេញ។ ការ push ទៅ
`release/**` មិនចាប់ផ្ដើមពួកវាទេ (2026-10-18)៖ ការផ្លាស់ប្ដូរនីមួយៗបានដំណើរការ matrix រួចហើយនៅលើ PR របស់វា
ហើយការរួមបញ្ចូលដែលបាន merge គឺជាការងាររបស់ Release-Green (`docs/ops/RUNNER_BOX.md` → lane ដែលបាន host)។ Fork
និង merge group ប្រើ runner ដែលបាន host សម្រាប់ការងារដែលបើមិនដូច្នោះទេនឹងជ្រើសរើស runner ដែល host ដោយខ្លួនឯង;
ត្រូវផ្ទៀងផ្ទាត់ថាមានសមត្ថភាព runner ដែលបាន host គ្រប់គ្រាន់ មុនពេលដាក់ឱ្យប្រើប្រាស់។

បង្កាន់ដៃ JSON នីមួយៗកំណត់អត្តសញ្ញាណ SHA ដែលបាន checkout, ការដំណើរការ workflow និងលើកសាកល្បង។
CLI បដិសេធភាពមិនត្រូវគ្នារវាង SHA របស់ checkout/event។ ការធ្វើតេស្ត workflow ចងសមាជិកភាពគោលការណ៍
ទៅនឹងបញ្ជី `needs` របស់ការងារលទ្ធផលវិនិច្ឆ័យ ដូច្នេះ lane ថ្មី ឬដែលបានដកចេញ មិនអាចបាត់ដោយស្ងៀមស្ងាត់បានទេ។
បង្កាន់ដៃទាំងនេះគ្របដណ្ដប់តែ workflow របស់ខ្លួនប៉ុណ្ណោះ មិនមែនការបោះពុម្ពផ្សាយ ការដាក់ឱ្យដំណើរការ ឬសមាសភាគខាងក្នុង
របស់ scanner ផ្ដល់យោបល់ដែលមានស្រាប់ទេ។ ការធ្វើឱ្យឈ្មោះ check ទាំងពីរសកម្មក្នុងច្បាប់ branch គឺជា
ការផ្លាស់ប្ដូរផ្នែករដ្ឋបាលដាច់ដោយឡែកមួយ; ការបន្ថែមការងារទាំងនេះមិនការពារ branch ដោយខ្លួនវាឡើយ។

### សមត្ថភាពប្រតិបត្តិការ UI

CI ដំណើរការបញ្ជី UI ពេញលេញជា matrix shard `test-vitest` ចំនួនបួន ដែលនីមួយៗមាន worker ច្រើនបំផុត
បួន និងកាលកំណត់ការងារ 15 នាទីដែលមានស្រាប់។ Shard ទីមួយក៏ដំណើរការ
ឈុត Vitest របស់ MCP/autoCombo ផងដែរ។ លទ្ធផលការងារចាំបាច់គ្របដណ្ដប់គ្រប់ផ្នែកនៃ matrix; ការបរាជ័យ
ឬការលុបចោល shard មួយ មិនអាចបញ្ជាក់ការទទួលយកបេក្ខភាពបានទេ។

កម្មវិធីសង្កេតប្រចាំយប់រក្សាទុកបង្កាន់ដៃបេក្ខភាពជាក់លាក់ដាច់ដោយឡែកសម្រាប់ UI shard នីមួយៗ
រួមទាំងការប្រតិបត្តិ MCP នៅក្នុងបង្កាន់ដៃទីមួយ។ បង្កាន់ដៃទាំងបួន កំណត់ហេតុ និង
អត្តសញ្ញាណប្រតិបត្តិការដែលត្រូវគ្នា សុទ្ធតែចាំបាច់។ `npm run test:vitest:ui` នៅមូលដ្ឋាននៅតែជ្រើសរើស
ឈុតពេញលេញ; ការដំណើរការ `--shard` មួយគ្រាន់តែជាភស្តុតាងមួយផ្នែកប៉ុណ្ណោះ។

### បញ្ជីស្កេនឋិតិវន្ត

បញ្ជី npm-alias ដែលមានកំណែ និងសមាជិកភាពស្កេនឋិតិវន្ត ស្ថិតនៅក្នុង
`config/quality/gate-manifest.json`។ ដំណើរការ `npm run check:gate-manifest` ដើម្បីផ្ទៀងផ្ទាត់
ឈ្មោះ script និងពាក្យបញ្ជាជាក់លាក់ធៀបនឹង `package.json`; ការបន្ថែម ការដកចេញ និង
ភាពប្រែប្រួលនៃពាក្យបញ្ជា នឹងធ្វើឱ្យទាំង hook មូលដ្ឋាន និងការងារចាត់ថ្នាក់ការផ្លាស់ប្ដូរក្នុង CI បរាជ័យ។
Alias មិនមែនជាការងារ workflow, instance របស់ matrix ឬករណីតេស្តទេ៖ ចំនួនទាំងនេះ
មិនត្រូវបង្ហាញថាអាចជំនួសគ្នាបានឡើយ។

ប្រើ `npm run quality:scan -- --list` ឬ `npm run quality:scan:fast -- --list`
ដើម្បីពិនិត្យ alias ដែលបានជ្រើសរើសដោយមិនប្រតិបត្តិពួកវា។ Runner ហៅ
ចំណុចចូល npm ដូច្នេះ runtime របស់វា (រួមទាំង Bun នៅកន្លែងដែលបានកំណត់រចនាសម្ព័ន្ធ) ត្រូវបានរក្សាទុក។

working tree; សម្រាប់គ្រប់ key ដែលតម្លៃជាភាសាអង់គ្លេសបានផ្លាស់ប្តូរ locale ណាមួយដែលនៅតែរក្សា

មិនអាចបង្ហាញថាការបកប្រែដែលមានជាយូរមកហើយ កើតចេញពីភាសាអង់គ្លេសចាស់មួយណាទេ ដូច្នេះ gate វាយតម្លៃ

   (`src/i18n/request.ts::deepMergeFallback`, #7258) ហើយ key នឹងចូលជួររង់ចាំការបកប្រែ។

ប្រសិនបើ **អត្ថន័យ** របស់ string បានផ្លាស់ប្តូរ គួរតែជ្រើសរើស **ប្តូរឈ្មោះ key**៖ key ថ្មីមិនអាចទទួលមរតក

**កែតម្រូវមូលហេតុដើម; ប្រើ allowlist តែនៅពេលការបំពានមានស្រាប់ ហើយ
មិនអាចកែតម្រូវក្នុង PR ដូចគ្នាបានប៉ុណ្ណោះ។**

នៅពេលបន្ថែមធាតុមួយទៅក្នុង allowlist៖

1. ដាក់បញ្ចូល comment ដែលមានហេតុផលបញ្ជាក់។
2. យោងទៅ tracking issue (ឧ., `// #3498 — Phase 2 feature, not yet implemented`)។
3. លុបធាតុនោះនៅក្នុង PR ដូចគ្នាដែលកែតម្រូវការបំពាន — ធាតុហួសសម័យដែលលែង
   ទប់ស្កាត់ការបំពានសកម្ម គឺជាកំហុសមួយដោយខ្លួនឯង (ការអនុវត្តច្បាប់លើធាតុហួសសម័យ 6A.3 នឹង
   ធ្វើឱ្យ gate បរាជ័យលើធាតុ allowlist ដែលលែងមានការយោង នៅពេលបានអនុវត្តរួច)។

**កុំ**បន្ថែមធាតុ allowlist ដើម្បីធ្វើឱ្យការធ្វើតេស្តជោគជ័យលឿនជាងមុន។ gate ពណ៌បៃតងដែលមាន
allowlist កាន់តែធំឡើង បង្កើតតែអារម្មណ៍ក្លែងក្លាយអំពីគុណភាពប៉ុណ្ណោះ។

### នៅពេល gate បរាជ័យលើ PR របស់អ្នក

1. **អាន output របស់ gate ដោយប្រុងប្រយ័ត្ន** — វាប្រាប់អ្នកយ៉ាងច្បាស់ថា file ឬ symbol មួយណាបានបំពាន
   ច្បាប់។
2. **កែតម្រូវការបំពាន** — gate ភាគច្រើនជាការត្រួតពិនិត្យ filesystem ដែលមានលទ្ធផលកំណត់ច្បាស់ ហើយនឹងជោគជ័យភ្លាមៗ
   នៅពេល code ត្រឹមត្រូវ។
3. **ប្រសិនបើការបំពានមានស្រាប់** (មានន័យថា អ្នកមិនបានបង្កើតវាទេ ប៉ុន្តែឥឡូវនេះ gate
   គ្របដណ្តប់លើវា)៖ បន្ថែមធាតុ allowlist ដោយមាន comment បញ្ជាក់ហេតុផល និង tracking issue។
4. **ប្រសិនបើ gate ជា ratchet** (coverage, ការព្រមាន ESLint, ការស្ទួន, complexity)៖
   ការផ្លាស់ប្តូររបស់អ្នកបានធ្វើឱ្យ metric កាន់តែអាក្រក់។ កែតម្រូវបញ្ហាមូលដ្ឋាន ឬ (ក្នុងករណីកម្រ) ដំណើរការ
   `npm run quality:ratchet -- --update` ប្រសិនបើការផ្លាស់ប្តូរនោះធ្វើឡើងដោយចេតនា ហើយការធ្លាក់ចុះនៃ metric
   អាចទទួលយកបាន — ប៉ុន្តែត្រូវកត់ត្រាហេតុផលនៅក្នុងសេចក្តីពិពណ៌នា PR។
5. **gate ផ្តល់ដំបូន្មាន** (`continue-on-error: true`) គឺសម្រាប់ផ្តល់ព័ត៌មាន — វាមិនរារាំង
   ការបញ្ចូលចូលគ្នាទេ ប៉ុន្តែបង្ហាញនៅក្នុងសេចក្តីសង្ខេប CI។ ទោះយ៉ាងណាក៏ដោយ សូមកែតម្រូវវា។

6. ធ្វើបច្ចុប្បន្នភាពឯកសារនេះ (បន្ថែមជួរដេកមួយទៅតារាងកិច្ចការដែលពាក់ព័ន្ធ)។

### បញ្ចូលចូលគ្នា / លុបភាពស្ទួន (បែបមេកានិច ហានិភ័យទាបជាង)

បេក្ខភាពនីមួយៗត្រូវបានផ្ទៀងផ្ទាត់ទល់នឹងស្ថានភាព gate ជាក់ស្តែងនៅថ្ងៃទី 2026-06-17 (ជឿទុកចិត្ត ប៉ុន្តែត្រូវផ្ទៀងផ្ទាត់);
ការបញ្ចូលចូលគ្នាដែលមើលទៅ "ជាក់ស្តែង" មួយចំនួន បែរជាលាក់បំណុល ហើយ **មិនមែន** ជាការជំនួសដោយផ្ទាល់ដែលស្អាតនោះទេ។
